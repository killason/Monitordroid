# Modbus RTU Monitor for Android

Небольшой монитор **Modbus RTU** для Android на Python/Kivy.  
Программа предназначена для работы с USB → RS485 адаптерами через Android USB Host API.

Проект рассчитан прежде всего на запуск в **Pydroid 3** на Android.

## Возможности

- подключение USB → RS485 адаптера;
- автоматическое обнаружение **Prolific PL2303** по VID/PID `067B:2303`;
- запрос и ожидание Android USB permission;
- открытие последовательного порта;
- параметры порта:
  - `9600 baud`
  - `8N1`;
- непрерывное чтение входящего USB serial потока;
- разбор потока на отдельные кадры Modbus RTU;
- проверка CRC-16 Modbus;
- отображение времени получения кадра;
- отображение RX-кадров построчно;
- автоматическая прокрутка вниз во время мониторинга;
- ручная прокрутка накопленного лога пальцем;
- сохранение лога в `.txt`;
- выбор директории сохранения;
- автоматическое имя файла по текущей дате и времени.

### `android_serial.py`

Низкоуровневый Android USB serial слой.

Отвечает за:

1. поиск USB-устройства;
2. проверку USB permission;
3. запрос permission;
4. открытие serial-порта.

Для текущего проекта используется:

```text
VID = 0x067B
PID = 0x2303
```

Это Prolific PL2303.

**Важно:** этот модуль не содержит логики Modbus и не должен зависеть от Kivy GUI.

### `modbus_method.py`

Вся логика Modbus RTU.

Модуль отвечает за:

- CRC-16;
- проверку CRC;
- определение допустимой длины кадра;
- сборку кадра из произвольных фрагментов входного потока;
- обработку нескольких кадров, пришедших одним чтением;
- ресинхронизацию при повреждённых данных;
- извлечение адреса;
- извлечение функции;
- определение exception response;
- форматирование кадра для вывода.

Модуль не зависит от Android и Kivy.

Это позволяет в будущем использовать тот же parser с обычным `pyserial` на Linux/Windows.

### `monitor_main.py`

GUI и связывающий слой приложения.

Отвечает за:

- Kivy-интерфейс;
- кнопки START / STOP / SAVE;
- USB initialization;
- запуск чтения;
- передачу полученных байтов в `ModbusRTUParser`;
- вывод распознанных кадров;
- сохранение лога.

## Почему parser не использует размер USB-чтения как границу Modbus кадра

USB serial transport возвращает поток байтов произвольными порциями.

Например, один вызов чтения может вернуть:

```text
0B 03 00
```

а следующий:

```text
01 00 0F 54 A4
```

Или один вызов может сразу содержать несколько Modbus кадров.

Поэтому граница результата `read()` **не является границей Modbus RTU кадра**.

Parser сначала накапливает байты во внутреннем буфере, затем определяет возможные размеры кадра по структуре конкретной функции Modbus и подтверждает найденный кадр CRC.

## Modbus RTU framing

Modbus RTU не содержит специального символа окончания кадра.

Структура кадра зависит от Modbus function code.

Parser использует соответствующие структуры запросов и ответов, а CRC используется как проверка найденной границы.

В частности, учитываются стандартные функции:

- `01` Read Coils
- `02` Read Discrete Inputs
- `03` Read Holding Registers
- `04` Read Input Registers
- `05` Write Single Coil
- `06` Write Single Register
- `0F` Write Multiple Coils
- `10` Write Multiple Registers
- `16` Mask Write Register
- `17` Read/Write Multiple Registers

Также обрабатываются exception responses.

## Требования

### Android

Рекомендуется:

- Android 6 или новее;
- USB OTG;
- USB Host support;
- USB → RS485 адаптер на базе PL2303.

Текущая разработка проверялась на Android 13.

### Python

Проект разрабатывается в Pydroid 3.

Используемые компоненты:

- Python 3.x
- Kivy
- usb4a
- usbserial4a
- pyjnius

## Установка

Установить зависимости:

```bash
pip install -r requirements.txt
```

Если используется Pydroid 3, запускать приложение через **Play**, а не как обычный Python-процесс из терминала.

Это важно для Android-интеграции: доступ к Android USB Host API должен выполняться внутри Android/Kivy runtime.

## Подключение

1. Подключить USB → RS485 адаптер через OTG.
2. Запустить приложение.
3. Приложение ищет:

```text
PL2303 067B:2303
```

4. При первом подключении Android может показать запрос USB permission.
5. После получения permission порт открывается.
6. Нажать **СТАРТ**.
7. Входящие корректные Modbus RTU кадры появляются в логе.

## Текущие параметры последовательного порта

По умолчанию:

```text
Baudrate: 9600
Data bits: 8
Parity: None
Stop bits: 1
```

В коде:

```python
BAUDRATE = 9600
```

и при открытии:

```python
bytesize=8
parity="N"
stopbits=1
```

## Работа с логом

Во время мониторинга новые кадры автоматически добавляются в нижнюю часть списка.

Когда мониторинг остановлен:

- автоматическая прокрутка отключается;
- лог можно листать пальцем вверх и вниз.

Лог построен на:

```text
ScrollView
└── BoxLayout
    ├── Label
    ├── Label
    ├── Label
    └── ...
```

Это сделано намеренно: обычный Kivy `ScrollView` обеспечивает стабильную touch-прокрутку на Android.

## Сохранение

Кнопка **СОХРАНИТЬ** открывает выбор директории.

Имя по умолчанию формируется автоматически:

```text
YYYY-MM-DD_HH-MM-SS.txt
```

Например:

```text
2026-09-05_13-54-27.txt
```

Имя можно изменить перед сохранением.

## Архитектурный принцип

Проект разделён на три независимых слоя:

```text
              ┌─────────────────────┐
              │    monitor_main.py   │
              │     Kivy / GUI       │
              └──────────┬──────────┘
                         │
              raw bytes / frames
                         │
              ┌──────────▼──────────┐
              │  modbus_method.py   │
              │    Modbus RTU       │
              │       parser        │
              └─────────────────────┘

              ┌─────────────────────┐
              │  android_serial.py  │
              │ Android USB Serial  │
              └─────────────────────┘
```

Главная идея:

**транспорт не должен знать о Modbus, а Modbus parser не должен знать об Android.**

Благодаря этому в будущем можно заменить только транспорт:

```text
Android USB / usbserial4a
          ↓
android_serial.py
```

на:

```text
Linux / Windows
          ↓
pyserial
```

а `modbus_method.py` оставить тем же.

## Важное ограничение

Текущая версия — именно **монитор/сниффер**.

Она не является полноценным Modbus Master и не отправляет запросы автоматически.

Она принимает входящий serial stream, выделяет корректные Modbus RTU кадры и показывает их в интерфейсе.
